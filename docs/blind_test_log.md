# 真实项目盲测记录（阶段 1）

目的：回答「**「本次引入的回归」的判断能不能被信任**」。误报（判成回归但行为其实没坏）
是这个产品的生命线；盲测就是量化它。

> 与 `docs/mutation_eval_results.md`（示例服务变异评估）的区别：那里的缺陷是人为注入、
> 预期由程序推导，只能证明引擎与这套演示规则有效；**真实误报率只能来自真实改动**。

## 盲测协议（每轮 30~60 分钟）

1. **选改动**：找一个真实项目里由 AI（或人）改完、尚未合并的改动。准备好「修改前」与
   「修改后」两个可访问环境（或 commit + 启动命令，自己起两份）。
2. **写需求**：把这次改动要达到的需求写成 3~10 条验收点（可以是你自己，也可以是另一个
   没看过代码细节的人/模型）。
3. **写规则**：在验收器里把验收点翻译成检查（或让 AI 建议后人工确认）。**规则一旦确认
   不再修改**；要改就存新版本，并记录「在原版本上为什么发现不够」。
4. **运行验收**，导出 Markdown 报告。
5. **对照真值**：你自己（或改动作者）先写下这个改动的已知问题清单（哪些行为被有意改变了、
   哪些 bug 是已知的、哪些是这次新引入的），再和报告逐条对照。
6. **填记录表**（下方模板），并把两处特别重要的数字填进汇总表。

**规则**：写规则的人不应提前知道「哪里改坏了」。如果你既是改动作者又是规则作者，
请在记录里注明（会把误报率的可信度打折）。

## 要记录的数字

| 指标 | 定义 |
| --- | --- |
| 回归误报 FP | 报告判为「本次引入的回归」，但对照真值其实是正常行为变化/原有问题 → **必须为 0** |
| 回归漏报 FN | 真值中存在本次引入的回归，但报告没判出来（判成通过/原有问题/无法判断） |
| 无法判断占比 | 无法判断的检查数 ÷ 总检查数（环境问题会拉高这个值，需要单独排查） |
| 规则编写耗时 | 从读需求到规则确认的实际分钟数 |
| 规则轮次 | 确认前改了几版（说明第一版规则的质量） |
| 需求未满足误判 | 「新需求未满足」判错（把满足判成未满足，或反之） |

## 合格线（建议，先执行 5~10 轮再调整）

- 回归误报 FP：**0**。出现任何一次误报，先停下来定位是「规则错误」还是「引擎错误」，
  修复并记录，然后重跑该轮。
- 回归漏报 FN：允许存在，但每轮要写明漏掉的原因（规则没覆盖 / 规则写错 / 引擎问题）。
- 无法判断占比：> 20% 时该轮结论视为不可用，先修环境。
- 规则编写耗时：记录基线，观察「AI 建议 + 人工确认」是否把它压低。

## 每轮记录模板

```markdown
### 第 N 轮 · YYYY-MM-DD

- 项目 / 改动：
- 改动来源：AI 生成 / 人工 / 混合
- 环境：baseline=… candidate=…（或 commit 与启动命令）
- 写规则的人：本人 / 其他人 / 模型（是否提前知道改动细节：是/否）
- 需求条数 → 检查条数：
- 规则版本：v?（确认前改了几版：?）；规则编写耗时：? 分钟

**报告结论**：（一句话，如「发现 2 项回归」）

**真值清单**：
- 本次新引入的问题：…
- 有意改变的行为：…
- 已知原有问题：…

**对照**：
- 回归误报（FP）：0 / 有 → 具体条目与原因：
- 回归漏报（FN）：无 / 有 → 具体条目与原因（规则没覆盖 / 规则写错 / 引擎问题）：
- 需求未满足误判：无 / 有 → …
- 无法判断：? 条（原因：环境 / 超时 / 取消）

**改进项**：
- 对规则的：…
- 对产品的（分类、报告措辞、UI）：…
```

## 结束条件（阶段 1 的退出标准）

- 完成 ≥ 5 轮真实项目盲测，且最近 3 轮回归误报 = 0；
- 汇总出一份「分类/报告措辞/规则编写」的修正清单，并回填到 README 的已知限制与
  `docs/mutation_eval_results.md` 的方法说明里；
- 再决定阶段 2 做什么（或者证明这件事不值得继续投入）。
